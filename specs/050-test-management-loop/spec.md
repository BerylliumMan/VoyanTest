# Feature Specification: 测试管理闭环（计划 / 轮次 / 任务 / 评论 / 评审）

**Feature Branch**: `050-test-management-loop`
**Created**: 2026-11-11
**Status**: Draft
**Input**: User description: "先做 P1：把回归计划升级为计划/轮次/任务分配，补用例评论与人工评审。"

## 背景

047/048/049 已经把「变更 → 自动补用例 → 执行 → 失败分类 → 环境重试 → 通知」这条自动化链路打通，但**人的那一层仍然是空的**：

1. 没有「测试计划」：项目里只有用例列表和套件，谁负责哪些用例、这一轮要验什么、什么时候截止，全靠口头/外部表格。
2. 没有「轮次」：042 的 `QualityRegressionPlan` 只是「一组用例 + 最近批次」，没有生命周期、没有用例快照，改一次计划就回不到上一轮的口径。
3. 没有任务归属：计划项不能指派给人，也没有「我的待办」，执行结果和人的责任对不上。
4. 没有协作：用例不能评论、不能 @ 人、没有人工评审（只有 041 的 AI 用例评审）。

本特性补的是**管理层**，不改变执行语义：失败判定、分类、自愈仍由现有执行器负责；新增的是计划、轮次、任务、评论、评审五块，以及它们与既有批次/报告的连接。

**非目标**：组织/多租户/RBAC（需要单独立项）；外部缺陷系统集成；移动端。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建测试计划并维护用例 (Priority: P1)

项目成员在「测试计划」页新建计划（名称、描述、可选需求、负责人、起止日期），从项目用例中批量加入计划项，并为每一项设置优先级、负责人、截止日期和备注。计划列表显示当前进度；详情页能按模块/负责人筛选计划项。

**Why this priority**: 计划是轮次、任务、进度的载体；没有计划，后面四件事都没有挂靠点。

**Independent Test**: 在一个有若干用例的项目里新建计划、加入 3 条用例、刷新页面，计划项与进度（0/3）正确；删除一条用例后计划项显示「用例已删除」且不阻塞后续轮次。

**Acceptance Scenarios**:

1. **Given** 项目成员打开计划页，**When** 新建计划并加入 3 条用例，**Then** 计划详情显示 3 个计划项、进度 0%，列表页显示该计划。
2. **Given** 同一计划已包含用例 A，**When** 再次批量加入 A 与 B，**Then** A 不重复、B 追加成功，返回「新增 1 / 跳过 1」。
3. **Given** 计划项对应用例被删除，**When** 查看计划详情，**Then** 该项显示「用例已删除」，进度统计不计入它，后续轮次自动跳过。
4. **Given** 项目 A 的计划，**When** 无项目 A 权限的用户访问，**Then** 返回 403 且列表不可见。
5. **Given** 计划处于 active，**When** 用户归档，**Then** 计划从默认列表消失但历史轮次/报告仍可访问。

---

### User Story 2 - 创建轮次并执行 (Priority: P1)

从计划创建轮次：命名、选择环境（默认计划环境）、勾选本轮要执行的用例（默认全部），轮次保存用例快照。点击「开始」后创建运行批次并执行；执行完成后轮次显示通过/失败数与通过率，计划项状态自动更新为 passed/failed。

**Why this priority**: 这是计划真正「跑起来」的一步，也是本特性与现有执行引擎的唯一连接点。

**Independent Test**: 用 3 条用例（1 通过、1 断言失败、1 环境失败）创建轮次并执行，轮次状态 completed、统计 1/3、计划项状态分别为 passed/failed/failed，报告链接可打开批次详情。

**Acceptance Scenarios**:

1. **Given** 计划有 3 条用例，**When** 创建轮次（默认全部）并开始，**Then** 生成一个 `source='test_cycle'` 的批次，轮次状态 running，页面可跳转批次报告。
2. **Given** 轮次正在运行，**When** 再次点击开始，**Then** 返回 409「轮次正在执行」，不产生第二个批次。
3. **Given** 批次执行完成，**When** 轮次详情刷新，**Then** 状态 completed、通过/失败计数与批次一致，计划项状态按用例结果更新。
4. **Given** 轮次中部分用例失败，**When** 点击「重跑失败」，**Then** 新建批次并归属于同一轮次，轮次最新批次指向新批次，进度随之更新。
5. **Given** 轮次没有可执行用例（全被删除或未勾选），**When** 点击开始，**Then** 返回 400「没有可执行的用例」。
6. **Given** 批次被停止/取消，**When** 轮次收尾，**Then** 轮次状态 cancelled，不触发 049 的自动重试。

---

### User Story 3 - 任务分配与我的待办 (Priority: P1)

计划项可以指派给项目成员并设置截止日期。成员在「我的待办」页看到所有项目里分配给自己的计划项，按「待处理 / 逾期 / 已完成」筛选；逾期项高亮。轮次执行完成后，计划项状态自动同步为通过/失败，也允许负责人手动标记「阻塞」。

**Why this priority**: 没有归属，计划只是另一张用例列表；「我的待办」是把平台推进日常工作流的入口。

**Independent Test**: 把两条计划项分别指派给用户 A/B，A 登录后只看到自己的两条（跨两个项目各一条），逾期筛选只返回过期且未完成项。

**Acceptance Scenarios**:

1. **Given** 计划项指派给用户 A 且截止日期在未来，**When** A 打开「我的待办」，**Then** 看到该项（含项目、计划、用例名、截止日期）。
2. **Given** 计划项截止日期早于今天且状态不是 passed，**When** 打开「逾期」筛选，**Then** 该项出现且高亮。
3. **Given** 轮次执行完成，**When** 查看计划项，**Then** 状态自动变为 passed 或 failed；负责人手动改为 blocked 后，下一次轮次完成才会被覆盖。
4. **Given** 非项目成员被指定为负责人，**When** 保存，**Then** 返回 400「负责人不在项目成员中」。
5. **Given** 指派保存成功，**When** 被指派人查看通知中心，**Then** 有一条「你被分配了测试任务」通知。

---

### User Story 4 - 用例评论与 @ 提及 (Priority: P2)

在用例详情里查看/发表评论，支持 `@用户名` 提及；被提及者与用例关注者收到站内通知。评论按时间倒序展示，作者可编辑/删除自己的评论，管理员可删除任意评论。

**Why this priority**: 协作的最小单元；没有评论，评审结论只能落在外部聊天里。

**Independent Test**: 用户 A 在用例下评论并 @B，B 的通知中心出现一条提及通知；A 编辑评论后内容更新；B 删除 A 的评论返回 403。

**Acceptance Scenarios**:

1. **Given** 用例详情，**When** 发表评论「@bob 这里断言太宽」，**Then** 评论出现在列表顶部，bob 收到「有人在用例中提到了你」通知。
2. **Given** 评论作者，**When** 编辑评论，**Then** 内容更新且保留原发布时间、记录编辑时间。
3. **Given** 非作者且非管理员，**When** 删除评论，**Then** 返回 403。
4. **Given** 评论正文为空或超过 5000 字，**When** 提交，**Then** 返回 422。
5. **Given** 无项目权限的用户，**When** 读取该用例评论，**Then** 返回 403。

---

### User Story 5 - 人工评审 (Priority: P2)

用例可以发起人工评审：选择评审人（项目成员）、填写说明；评审人在「待我评审」里看到任务，给出「通过 / 需要修改 / 驳回」并附评论。发起人与评审人收到通知，用例详情展示最新评审状态与历史。

**Why this priority**: 与 041 的 AI 评审互补——AI 给建议，人对结果负责；上线前的人工卡点是测试管理平台的常见诉求。

**Independent Test**: A 对用例发起评审给 B，B 在待评审列表通过并评论；A 收到通知，用例状态变为「已通过」，历史中可见 B 与评论。

**Acceptance Scenarios**:

1. **Given** 用例，**When** A 发起评审并选择 B，**Then** 生成 pending 评审，B 收到通知，用例显示「待评审」。
2. **Given** B 打开待评审列表，**When** 点击通过并填写评论，**Then** 评审状态 approved，A 收到通知，历史新增一条。
3. **Given** B 选择「需要修改」，**When** 提交，**Then** 用例状态为 changes_requested，A 可修改后重新发起。
4. **Given** 同一用例已有 pending 评审，**When** 再次发起，**Then** 返回 409「已有待处理评审」。
5. **Given** 评审人是发起人自己，**When** 提交，**Then** 返回 400「不能评审自己发起的用例」。
6. **Given** 用例被删除，**When** 评审人处理，**Then** 返回 404，队列自动清理。

---

### Edge Cases

- 计划归档后：默认列表不显示，历史轮次与报告仍可打开；恢复为 active 后可继续建轮次。
- 计划项用例被删除：显示「用例已删除」，轮次创建时跳过并在轮次详情标注「跳过 N 条」。
- 轮次启动与批次创建之间服务重启：以轮次状态与 `batch_id` 为准，不重复建批次；孤儿批次由启动检查标记为 cancelled（复用 049 的收尾校验思路）。
- 同一计划下并发创建轮次：允许（不同轮次可排队），但同一时刻只允许一个 running 轮次；第二个启动返回 409。
- 评论正文里的 `@` 后跟不存在用户名：按普通文本处理，不报错、不通知。
- 评审人离职/被移出项目：待评审列表仅返回当前仍有项目权限的评审人任务；管理员可转交（v1 仅支持管理员取消）。
- 时区：截止日期按服务端本地时区（Asia/Shanghai）计算「今天」；存储为 UTC。
- 历史数据：上线前没有计划/轮次，不影响既有用例、批次、报告。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** 系统 MUST 提供项目级测试计划 CRUD，计划包含名称、描述、可选需求关联、负责人、起止日期、状态（draft/active/completed/archived）。
- **FR-002** 系统 MUST 支持批量向计划添加用例（去重），并为计划项设置优先级、负责人、截止日期、备注与排序。
- **FR-003** 系统 MUST 提供计划进度：总项数、已通过、已失败、未开始、已阻塞、已删除用例数；进度 = 已通过 / 有效项数。
- **FR-004** 系统 MUST 支持从计划创建轮次，轮次保存用例快照（创建后不受计划项增删影响），可指定环境与 Agent。
- **FR-005** 系统 MUST 支持启动轮次：创建 `source='test_cycle'`、`source_id=<cycle_id>` 的运行批次，并把批次与轮次关联；同一时刻同一计划只允许一个 running 轮次。
- **FR-006** 系统 MUST 在批次收尾时把结果回填到轮次与计划项：轮次 completed/cancelled、通过/失败计数、计划项 passed/failed；环境类自动重试的行为保持 049 语义不变。
- **FR-007** 系统 MUST 支持轮次内「重跑失败」，新批次仍归属该轮次，轮次进度以最新批次为准。
- **FR-008** 系统 MUST 提供「我的待办」：跨项目聚合当前用户被指派的计划项，支持待处理/逾期/已完成筛选；逾期 = 截止日期早于今天且状态非 passed。
- **FR-009** 系统 MUST 提供用例评论：列表、发表、编辑、删除；支持 `@用户名` 提及并在通知中心通知被提及者。
- **FR-010** 系统 MUST 提供人工评审：发起、待评审列表、通过/需要修改/驳回、取消（管理员）、历史记录；评审结论通知发起人。
- **FR-011** 所有新端点 MUST 复用项目权限过滤（admin 全量；tester 按 `user.project_ids`），越权返回 403。
- **FR-012** 所有写操作 MUST 记录审计日志（计划创建/归档、轮次启动/停止、评审结论）。
- **FR-013** 新表 MUST 通过启动期幂等 DDL 创建（沿用 `create_all` + `ALTER TABLE ... IF NOT EXISTS` 约定），不引入迁移框架。
- **FR-014** 通知 MUST 复用 `app/services/notifications.py` 的创建入口，不新增外发渠道。
- **FR-015** 前端 MUST 提供计划列表、计划详情（用例/轮次）、我的待办、用例评论与评审入口；不引入新的 UI 框架或外部资源。

### Key Entities

- **TestPlan**：项目级测试计划（名称、描述、需求、负责人、起止日期、状态）。
- **TestPlanItem**：计划中的一条用例（用例、负责人、优先级、截止日期、状态、备注、排序）；`(plan_id, case_id)` 唯一。
- **TestCycle**：计划的一次执行轮次（名称、环境、Agent、状态、最新批次、用例快照数、跳过数）。
- **TestCycleItem**：轮次用例快照（轮次、用例、计划项、负责人），创建时固化。
- **Comment**：用例评论（项目、用例、作者、正文、提及用户、创建/更新时间）。
- **CaseReview**：人工评审（用例、发起人、评审人、状态、评论、发起/处理时间）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** 用户可在 3 分钟内完成「建计划 → 加 3 条用例 → 建轮次 → 启动 → 看结果」全流程（真实环境）。
- **SC-002** 轮次完成后，计划项状态、轮次统计与批次报告三处数字一致（同一批次样本 100% 对齐）。
- **SC-003** 两个项目各指派 1 条计划项给同一用户，「我的待办」恰好返回 2 条；逾期筛选只返回过期未完成项。
- **SC-004** 评论 @ 提及后，被提及者通知中心 1 分钟内出现通知；无权限用户读取返回 403。
- **SC-005** 评审全流程（发起 → 通过/需要修改 → 通知 → 历史）在真实环境通过，且同一用例不能有两条 pending 评审。
- **SC-006** 新增单测/契约测试全部通过，既有全量单测无回归（基线 2161 passed）。

## Assumptions

- 单租户部署；项目成员 = 有该项目 `project_ids` 权限的用户或 admin。
- 复用现有 `users`、`projects`、`environments`、`test_cases`、`run_batches` 表，不改变现有执行语义。
- 截止日期按自然日比较，不做工作时间/节假日计算。
- 评论只做纯文本（前端按文本渲染，禁止 HTML），提及只解析 `@` + 用户名（不区分大小写，用户名唯一）。
- 通知只发站内通知，不接邮件/IM（P0 的渠道集成不在本特性范围）。
