# Feature Specification: 探索元素固化

**Feature Branch**: `045-explore-element-fixation`  
**Created**: 2026-10-30  
**Status**: Draft  
**Input**: User description: "给智能体一个流程文档，再告诉他项目的地址和用户密码信息，让他实际进行操作并生成自动化用例，并根据自己操作的元素进行固化"

## Clarifications

### Session 2026-10-30

- Q: 页面上有多个同名元素时，固化信息怎么区分？ → A: 候选定位列表（role+name 为主，层级/序号为备，按稳定性排序逐个尝试）
- Q: 何时判定固化定位失效并回退到动态定位？ → A: 失败即回退（先用固化定位，找不到/超时/点击无效才动态定位）
- Q: 已有历史用例（没有固化信息）怎么处理？ → A: 不批量补，旧用例照常执行，首次执行成功时自动写入固化信息

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 探索时记录元素并在生成用例时固化 (Priority: P1)

测试工程师上传一份流程文档，提供一个站点地址和测试账号。助手打开浏览器按文档实际操作（登录、点击导航、填表、提交），并把每一步**实际操作到的页面元素**记录下来。探索结束后生成 UI 自动化用例时，用例的交互步骤直接带上这些元素信息，而不是只有一句自然语言描述。

**Why this priority**: 这是用户诉求的核心。没有元素记录的用例，执行时每次都要靠模型重新猜元素，既慢又容易失败。

**Independent Test**: 对一个已知站点执行一次"文档 + 地址 + 账密"的探索，检查生成用例的交互步骤是否带有元素标识；把页面文本改掉（元素不变）后重放，步骤仍能定位到正确元素。

**Acceptance Scenarios**:

1. **Given** 用户提供流程文档、站点地址和账号密码，**When** 助手完成探索并生成用例，**Then** 交互类步骤带有该步实际操作的页面元素标识（角色 + 可访问名称）。
2. **Given** 同一步骤在探索中操作过多次，**When** 生成用例，**Then** 固化的是最后一次成功操作的元素，并保留候选元素用于回退。
3. **Given** 步骤只是校验类动作（如校验文案），**When** 生成用例，**Then** 不强行附带元素标识，避免错误绑定。

---

### User Story 2 - 执行时优先复用固化定位 (Priority: P1)

用例执行时，系统优先使用探索阶段固化的元素定位，而不是每一轮都让模型重新找元素。只有固化定位失效时，才回退到动态定位，并在成功后更新固化信息。

**Why this priority**: 固化的价值只有被执行侧真正消费才成立，否则只是多存了一份数据。

**Independent Test**: 同一用例连续执行两次，观察第二次是否直接使用固化定位；人为破坏固化定位后执行，应能通过动态定位成功并自动更新固化信息。

**Acceptance Scenarios**:

1. **Given** 用例步骤带有固化定位，**When** 执行，**Then** 直接按固化定位操作，不触发模型重新寻找元素。
2. **Given** 固化定位已失效（页面改版），**When** 执行，**Then** 自动回退动态定位；若成功，则更新该步骤的固化信息。
3. **Given** 回退后仍失败，**When** 执行结束，**Then** 失败原因明确区分"元素已变更"与"其他失败"。

---

### User Story 3 - 固化信息可查看与纠正 (Priority: P2)

用例详情里能看到每个步骤固化的元素信息，用户可以手动修正或清除（例如确实绑错了元素）。

**Why this priority**: 自动固化的结果不可能 100% 正确，人工纠正能力是可用性的兜底。

**Independent Test**: 打开用例详情，修改某步的固化元素并保存，重新执行时使用修改后的值。

**Acceptance Scenarios**:

1. **Given** 用例步骤已固化元素，**When** 用户打开详情，**Then** 能看到角色、名称与候选信息。
2. **Given** 用户修正或清除了固化信息，**When** 保存，**Then** 执行侧立即使用新值。
3. **Given** 用户清除了固化信息，**When** 执行，**Then** 回退到动态定位，恢复原有用例能力。

---

### Edge Cases

- 探索时元素来自弹窗、iframe 或动态生成的列表项，固化后重新打开页面已不存在。
- 同一角色 + 名称在页面上有多个（如多个"删除"按钮），需要能区分（层级或序号）。
- 页面语言/文案变更但元素结构未变：固化定位应继续有效。
- 探索中途失败或被用户停止：已成功的步骤仍应固化，未成功的不得凭空生成。
- 生成的是功能用例（手工）而非 UI 用例：不应写入执行用的元素定位。
- 既有历史用例没有固化信息：必须继续可执行，不得强依赖。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 探索过程 MUST 为每一次成功的页面操作记录元素标识（角色、可访问名称、候选定位）。
- **FR-002**: 探索报告 MUST 以结构化形式保留这些元素信息，而不是只把它们拼进自然语言摘要。
- **FR-003**: 生成 UI 自动化用例时，系统 MUST 把对应步骤的元素信息写入该步骤的结构化字段。
- **FR-004**: 生成功能用例（手工用例）时，系统 MUST NOT 写入执行用的元素定位。
- **FR-005**: 用例执行时 MUST 优先使用步骤的固化定位；固化定位不可用（找不到/超时/操作无效）时 MUST 立即回退到动态定位。
- **FR-006**: 动态定位成功且原固化定位失效时，系统 MUST 更新该步骤的固化信息。
- **FR-007**: 用例详情 MUST 展示每个步骤的固化元素信息，并允许用户修改或清除。
- **FR-008**: 固化信息 MUST 以候选定位列表形式保存（role+name 为主、层级/序号为备），按稳定性排序并逐个尝试，以区分同名元素。
- **FR-009**: 没有固化信息的历史用例 MUST 保持现有执行能力不变；首次执行成功时 MUST 自动写入固化信息（不批量补跑）。
- **FR-010**: 探索中途停止或失败时，系统 MUST 只固化已成功完成的步骤。
- **FR-011**: 固化信息的存储 MUST 复用现有步骤结构，不新增数据表。
- **FR-012**: 执行报告中 MUST 标注每步使用的是固化定位还是动态定位。

### Key Entities

- **探索步骤记录**：一次页面操作的动作、目标元素标识、候选定位、成功与否。
- **用例步骤**：原有的描述 + 预期结果，新增可选的固化元素信息。
- **候选定位**：同一元素的多条定位方式，按稳定性排序，用于回退。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 由探索生成的 UI 用例中，至少 80% 的交互步骤带有固化元素信息。
- **SC-002**: 同一用例第二次及以后执行的元素定位耗时，比首次执行降低 50% 以上。
- **SC-003**: 页面文案变化但元素结构不变时，固化定位的命中率不低于 95%。
- **SC-004**: 页面结构变化导致固化失效时，回退动态定位的成功率不低于 70%，且成功后固化信息被更新。
- **SC-005**: 用户在用例详情修正固化信息后，下一次执行立即使用新值（100%）。
- **SC-006**: 历史用例（无固化信息）的执行成功率与改动前相比不下降。

## Assumptions

- 元素标识以可访问性角色 + 可访问名称为主，CSS/XPath 作为候选回退。
- 固化信息存在现有步骤的结构化字段中，不新增表、不改变现有用例结构。
- 探索与生成仍走现有链路（文档 + 地址 + 账密 → 探索 → 生成），不新增入口。
- 执行侧已有动态定位与自愈能力，本特性是在其之前增加"优先使用固化定位"的一层。
- 本期只覆盖 UI 自动化用例，功能（手工）用例不涉及元素定位。
- 探索与执行的浏览器环境一致（同一站点、同一登录态要求），跨环境差异不在本期范围。
